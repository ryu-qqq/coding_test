# 부동산 계약 관리 (상태 머신, 실무 설계형) — 해설

> 막히기 전에 골격(`ContractManager.java`)부터 직접 채워보고, 그래도 안 풀리면 이 문서를 펼쳐보세요.

## 문제
계약은 `DRAFT → REVIEW → SIGNED → ACTIVE → CLOSED` 순서로만 한 칸씩 전진한다.
단계 건너뛰기, 뒤로 가기, 종료(CLOSED) 후 변경은 모두 금지.

## 핵심 직관 (1줄)
상태를 **enum** 으로 두고, "다음 상태가 무엇인가"를 enum 자신이 알게(`next()`) 하면
전이 규칙이 한 곳에 캡슐화된다.

## 자료구조
- `Map<String, ContractStatus> map` : 계약 id → 현재 상태.
- `enum ContractStatus` : 상태 + `next()` 전이 규칙.

## 알고리즘
1. `createContract(id)` : 이미 있으면 중복 예외, 없으면 `DRAFT` 로 등록.
2. `advance(id)` : 없으면 예외. 현재 상태의 `next()` 로 한 칸 전진해 저장.
3. `getStatus(id)` : 없으면 예외, 있으면 상태 문자열 반환.
4. `ContractStatus.next()` : switch 로 한 칸 다음을 반환하되 `CLOSED` 는 예외.

## 불변식
저장된 상태는 항상 정의된 5개 중 하나이며, `advance` 는 정확히 한 칸씩만 올린다.
→ 잘못된 전이(건너뛰기/역행)는 애초에 표현 불가능하다.

## 복잡도
- 모든 연산 O(1).

## 함정 ⚠️
- **CLOSED 에서 advance**: `next()` 가 예외를 던져야 한다. 안 하면 종료된 계약이 또 변한다.
- **없는 id**: `advance`/`getStatus` 둘 다 키 존재 확인. 안 하면 NPE.
- **중복 생성**: `createContract` 가 기존 id 를 덮어쓰면 진행 중인 계약이 DRAFT 로 초기화되는 사고.
- **enum 으로 "잘못된 전이"를 봉쇄**: String 으로 상태를 다루면 오타·임의 전이가 가능해진다.

## 대안 / 최적화
- 전이가 단순 선형이 아니라 분기(예: REVIEW→REJECTED)면 `Map<상태, Set<허용 다음 상태>>`
  전이표(transition table)로 일반화.
- 전이 시 부수효과(알림/감사로그)가 필요하면 상태 진입/이탈 훅을 둔다.

## 면접 답변 (한국어 1분)
> "정해진 순서로만 진행되는 상태 머신이라, 상태를 enum 으로 모델링했습니다. enum 에 next() 를 두어
> '다음 상태'를 상태 자신이 알게 했고, CLOSED 의 next() 는 예외를 던지게 해서 종료 후 전이를 막았습니다.
> Manager 는 계약 id→상태 맵만 들고, 없는 id 와 중복 생성을 예외로 방어합니다. 이렇게 하면 전이 규칙이
> enum 한 곳에 모여서, 순서가 바뀌어도 Manager 코드는 건드리지 않습니다."

## 설계 포인트
- **전이 규칙(enum) ↔ 저장/조회(Manager) 분리**: 상태 머신 자체는 enum 이 책임, Manager 는 컬렉션 관리만.
  → 전이 순서/규칙 변경은 `enum.next()` 만 수정. 저장 방식 변경(예: DB)은 Manager 만 수정.
- **확장 시 건드릴 곳**: 새 상태/분기 → enum + (필요 시) 전이표. 부수효과 → 전이 훅.

## Follow-up
- **분기 전이가 생기면?** `switch` 대신 `Map<상태, Set<다음 상태>>` 전이표로 검증.
- **전이 이력이 필요하면?** advance 시 (시각, from, to) 로그를 별도 리스트에 적재.
- **잘못된 전이 시도를 거부 vs 무시?** 정책으로 결정 — 여기선 예외(거부)로 명확히 실패시킴.
