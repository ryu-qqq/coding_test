# 오픈채팅방 (Programmers 42888) — 해설

> 막히기 전에 골격(`OpenChatRoom.java`)부터 직접 채워보고, 그래도 안 풀리면 이 문서를 펼쳐보세요.

## 문제
채팅방 로그를 처리한다. `Enter uid nick`(입장 메시지), `Leave uid`(퇴장 메시지), `Change uid nick`(닉만 변경, 출력 없음). 닉네임 변경은 **과거 메시지까지 소급** 적용되어, 모든 메시지는 그 사람의 최종 닉으로 출력된다.

## 핵심 직관 (1줄)
닉이 소급 적용되므로 "메시지 텍스트 확정"을 미뤄야 한다 → 최종 닉을 먼저 다 모은 뒤(1-pass), 다시 훑으며 메시지를 만든다(2-pass).

## 자료구조
- `Map<String, String> nick` : uid → 최종 닉네임 (덮어쓰기로 자연스럽게 "최종"이 됨).
- `List<String> out` : 출력 메시지 누적.

## 알고리즘 (2-pass)
1. **1-pass**: 모든 record 를 훑어 `Enter`/`Change` 면 `nick.put(uid, name)` (마지막 값이 최종 닉).
2. **2-pass**: 다시 훑으며 `Enter` → "최종닉님이 들어왔습니다.", `Leave` → "최종닉님이 나갔습니다." 추가. `Change` 는 무시.
3. `out.toArray(new String[0])`.

## 불변식
1-pass 종료 시 `nick[uid]` 는 그 uid 의 최종 닉네임. 2-pass 는 항상 이 최종값을 참조하므로 소급 적용이 자동 보장.

## 복잡도
- 시간: O(N) (record 를 두 번 선형 순회, split/맵 연산 O(1)).
- 공간: O(유저수 + 출력수).

## 함정 ⚠️
- **소급 적용 — 1-pass 에서 메시지를 만들면 망함**: Enter 시점의 닉으로 즉시 메시지를 만들면, 이후 Change 가 과거 메시지에 반영되지 않는다. 반드시 닉 확정을 끝낸 뒤 메시지를 생성.
- **Change 는 출력 없음**: 닉만 갱신. 2-pass 에서 Change 를 출력에 넣으면 오답.
- **split 토큰 수 차이**: `Enter`/`Change` 는 3토큰(cmd, uid, nick), `Leave` 는 2토큰(cmd, uid). `t[2]` 접근은 Leave 에서 하면 안 된다(인덱스 분기 주의).
- **List → String[]**: `toArray(new String[0])` (빈 배열 힌트 패턴). `toArray()` 만 쓰면 `Object[]` 라 캐스팅 문제.

## 대안 / 최적화
- 입장/퇴장 시 (이벤트타입, uid) 만 List 에 적재하고 닉 맵은 따로 갱신한 뒤, 마지막에 한 번에 메시지를 만들어도 동일(여전히 2-pass 성격). split 비용을 줄이려면 첫 공백/둘째 공백 위치를 indexOf 로 직접 찾아 substring.

## 면접 답변 (한국어 1분)
> "닉네임 변경이 과거 메시지까지 소급 적용된다는 게 핵심이라, 입장 시점에 바로 메시지를 만들면 안 됩니다. 그래서 2-pass 로 풀었습니다. 1차로 모든 로그를 훑어 uid→최종 닉 맵을 만드는데, Enter 와 Change 에서 닉을 덮어쓰면 자연히 마지막 값이 최종 닉이 됩니다. 2차로 다시 훑으며 Enter/Leave 만 그 최종 닉으로 메시지를 만들고 Change 는 건너뜁니다. Leave 는 토큰이 2개라 t[2] 에 접근하지 않도록 분기하는 게 함정이고, 결과는 toArray(new String[0]) 으로 String 배열로 변환합니다. record 를 두 번 도니 O(N) 입니다."

## Follow-up
- **1-pass 로 가능?** Enter/Leave 이벤트는 따로 적재하고 닉은 맵으로 관리한 뒤 마지막에 텍스트화하면 record 자체는 한 번만 훑지만, 결국 "메시지 텍스트 생성"을 뒤로 미루는 동일한 발상이다.
- **uid 별 동일 닉 중복?** uid 가 키라 닉 중복은 문제 없음. 닉이 메시지 표면에만 쓰이고 식별은 uid 로 한다.
