# [3차] 압축 (Programmers 17684) — 해설

> 막히기 전에 골격(`Compression.java`)부터 직접 채워보고, 그래도 안 풀리면 이 문서를 펼쳐보세요.

## 문제
LZW 압축의 단순화 버전. 사전에 A~Z 를 1~26 으로 등록한 뒤, 매 단계마다 사전에 있는 "가장 긴 접두사 w" 를 찾아 그 번호를 출력하고, `(w + 다음 글자)` 를 사전 다음 번호로 등록한다. 입력이 빌 때까지 반복.

## 핵심 직관 (1줄)
"사전에 있는 가장 긴 접두사"를 탐욕적으로 잘라 출력하고, 잘린 조각에 다음 한 글자를 붙여 사전을 키워간다.

## 자료구조
- `Map<String, Integer> dict` : 문자열 패턴 → 사전 번호. 초기 A~Z(1~26).
- `int next` : 다음에 부여할 사전 번호(27 부터).
- `List<Integer> out` : 출력 번호 누적 → 마지막에 `int[]` 변환.

## 알고리즘
1. 초기 사전: `for (char c='A'; c<='Z'; c++) dict.put(""+c, c-'A'+1)`.
2. 포인터 `i` 부터, 사전에 `msg[i..j)` 가 있는 동안 `j` 를 늘려 **최장 접두사 w** 를 찾는다.
3. `dict.get(w)` 출력에 추가.
4. 다음 글자가 있으면 `(w + 다음 글자)` 를 `next++` 번호로 등록.
5. `i = j` 로 진행, 입력 끝까지 반복.

## 불변식
매 단계 시작 시 `dict` 는 지금까지 등장한 모든 (이전패턴 + 1글자) 와 초기 A~Z 를 담는다. `out` 은 여기까지 압축된 코드열.

## 복잡도
- 시간: 각 글자에서 접두사 확장이 사전 조회 상수배 → 사실상 O(N) (substring/해시 비용 포함하면 O(N·평균패턴길이)).
- 공간: O(N) (사전 + 출력).

## 함정 ⚠️
- **최장 접두사 경계**: `while (j <= msg.length() && dict.containsKey(msg.substring(i, j))) j++;` 후 `j--`. 루프가 "더 이상 사전에 없을 때" 멈추므로 마지막으로 성공한 길이로 한 칸 되돌려야 한다. off-by-one 주의.
- **substring 끝 인덱스는 exclusive**: `msg.substring(i, j)` 는 `[i, j)`. `msg.substring(i, j+1)` 이 (w + 다음 글자).
- **다음 글자 존재 검사**: `if (j < msg.length())` 일 때만 사전 등록. 마지막 조각에서 빠뜨리면 IndexOutOfBounds.
- **char ↔ int 산술**: `c - 'A' + 1` 로 A→1. `String.valueOf(c)` 로 한 글자 문자열 키 생성.
- **List<Integer> → int[]**: `out.stream().mapToInt(Integer::intValue).toArray()` (`Integer::intValue` 언박싱).

## 대안 / 최적화
- 사전 조회를 `substring` 대신 인덱스 두 포인터로만 비교하거나, Trie 로 최장 접두사를 더 빠르게 찾을 수 있으나 N ≤ 1000 이라 Map 으로 충분.

## 면접 답변 (한국어 1분)
> "LZW 압축이라 사전을 Map<String,Integer> 로 두고 A~Z 를 1~26 으로 초기화했습니다. 다음 번호는 27부터요. 매 단계마다 현재 위치에서 사전에 존재하는 가장 긴 접두사를 길이를 한 칸씩 늘려가며 찾고, 더 이상 사전에 없으면 한 칸 되돌려 그게 w 입니다. w 의 번호를 출력에 넣고, 다음 글자가 있으면 w 에 그 글자를 붙인 새 패턴을 다음 번호로 등록한 뒤 포인터를 w 길이만큼 진행합니다. off-by-one, 즉 접두사 확장 루프를 멈춘 뒤 j 를 하나 되돌리는 것과, substring 끝 인덱스가 exclusive 라는 점이 함정입니다. N 이 1000 이하라 Map 조회로 충분히 빠릅니다."

## Follow-up
- **왜 (w + 다음 글자) 를 등록?** 다음에 같은 패턴이 더 길게 나오면 한 번에 압축하기 위해 점진적으로 사전을 키운다. 이게 LZW 의 핵심.
- **substring 비용이 부담되면?** 두 포인터로 직접 문자 비교하거나 Trie 를 쓰면 substring 객체 생성을 피할 수 있다.
